## 根因分类约定

参考岗位 JD 的归因口径，统一用这几类：

| 分类 | 含义 | 典型表现 |
|---|---|---|
| **检索失效** | 没检索到该检索的内容 | 上下文为空、检索到别的产品、召回不相关 |
| **指令歧义** | 提示词有歧义，模型理解偏了 | 该调工具没调、输出格式不对、越权回答 |
| **幻觉** | 模型编造了输入里没有的事实 | 编造称呼/历史/条款/金额 |
| **工具缺陷** | 工具本身参数设计或实现有问题 | 参数不可得被迫猜、异常返回不明确 |

## 新增案例模板

复制以下模板到 `NNN-短描述.md`，编号递增：

```markdown
# NNN: 一句话描述

- **发现时间**：YYYY-MM-DD
- **根因分类**：检索失效 / 指令歧义 / 幻觉 / 工具缺陷
- **严重级别**：高 / 中 / 低
- **状态**：已修复 / 观察中 / 待修复

## 1. 现象

用户/评测看到了什么（原话或原数据）。

## 2. 定位过程与证据

按顺序列出排查步骤和关键证据（日志片段、trace_id、DB 查询结果）。
**这一节是面试讲解的核心**：体现"如何用日志和链路追踪定位根因"。

## 3. 根因

一句话说清机制，而不是只描述现象。

## 4. 修复

| 层次 | 改了什么 |
|---|---|
| 代码/工具 | ... |
| 提示词 | ... |
| 数据 | ... |

## 5. 验证

修复后如何证明有效（测试、重跑评测的分数变化）。

## 6. 沉淀

可复用的原则是什么？配了哪些回归测试防止复发？
```

## 与 Langfuse Dataset 的关系

文档是"人读的案例"，Langfuse Dataset 是"机器跑的数据"：

1. 在 Langfuse `Tracing` 找到出问题的 trace
2. 点 **Add to Dataset**，把它沉淀成测试用例（输入 = 用户问题，期望 = 正确行为）
3. 攒够一批后，改提示词/工具时跑 Experiment，对比新旧版本在坏例上的表现

文档记录"为什么错"，Dataset 记录"错例本身"，两者互补。
