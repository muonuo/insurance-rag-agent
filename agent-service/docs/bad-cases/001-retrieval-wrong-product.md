# 001: 条款检索到错误产品的条款

- **发现时间**：2026-11-15
- **根因分类**：检索失效（工具参数错误）
- **严重级别**：高（检索全链路失效，回答不可用）
- **状态**：已修复（新增回归测试 `tests/test_product_lookup.py`）

## 1. 现象

离线 RAG 评测 8 题中 **5 题**检索上下文为空、6 个指标全为 0：

```
1. 回答172字 | 上下文1359字符
2. 回答215字 | 上下文2136字符
3. 回答75字  | 上下文2字符   ← []（空）
4. 回答88字  | 上下文2字符   ← []
5. 回答99字  | 上下文2字符   ← []
6. 回答1458字| 上下文3054字符
7. 回答121字 | 上下文2字符   ← []
8. 回答119字 | 上下文2字符   ← []
```

生产对话中表现为：用户问「太平洋小蜜蜂6号综合意外险的保险责任」，
AI 回答「检索到的条款并不是小蜜蜂6号，而是信美相互星辰守护B款少儿重疾险，无法回答」。

## 2. 定位过程与证据

**Step 1 · 先排除判卷器问题**
答题卡里 `retrieved_contexts` 本身就是空（`[]`），说明是检索阶段没拿到内容，
不是 RAGAS 判分异常。

**Step 2 · 重跑单题，打印工具调用记录**（关键证据）

```
调用工具: retrieve_insurance_clause 参数: {'query': '小蜜蜂6号 保险责任', 'k': 5, 'product_id': 1}
工具结果: {"ref-001": {"product_id": 1, "clause_name": "信美相互星辰守护B款少儿重疾险条款.pdf", ...}}
```

**模型传的 `product_id=1` 是猜的**，而该 ID 实际对应另一个产品。

**Step 3 · 确认工具签名**

`app/agents/tools/clause.py` 的旧签名要求 `product_id: int`，但模型只能看到产品**名称**
（用户问题里说的是"太平洋小蜜蜂6号…"），没有可靠的名称→ID 映射来源，只能猜。

## 3. 根因

**工具参数设计缺陷**：要求模型传入一个它无法获知的值（product_id），
模型只能猜测；猜错的 ID 检索到了别的产品条款，且工具不会报错——
返回的是"看似成功但内容错误"的结果，比直接失败更难发现。

## 4. 修复

| 层次 | 改了什么 |
|---|---|
| 工具 | `retrieve_insurance_clause` 改为 **`product_name` 优先**，由工具内部解析 ID（`_resolve_product_id`）；`product_id` 保留为兜底；查不到时明确返回"没有找到名为…的产品，请确认名称"，**禁止**用猜测值检索 |
| 数据访问 | `ProductRepository.find_by_name()`：名称归一化（去空格/标点）后精确匹配 → 双向包含匹配 → 多命中取名称最长者，兼容"太平洋小蜜蜂6号"与库中"小蜜蜂6号" |
| 提示词 | advisor / claim 两个 Agent 明确要求传产品全名到 `product_name`，禁止猜 `product_id` |

## 5. 验证

- 重跑同一题：`product_name='太平洋小蜜蜂6号综合意外险'` → 解析到 `product_id=10`，
  条款名 `太平洋小蜜蜂6号综合意外险条款.pdf`，**捕获 5 条上下文**，回答带正确引用
- 重建答题卡后全量评测：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| context_recall | 多题为 0 | 均值 0.898（0.75~1.0） |
| faithfulness | 多题为 0 | 均值 0.892（0.75~1.0） |
| answer_relevancy | 多题为 0 | 均值 0.817（0.61~1.0） |

## 6. 沉淀

**原则：不要要求模型传它无法获知的参数。** 能由服务端解析的，就让服务端解析；
解析不到时明确失败，不要让它猜。

回归测试（`tests/test_product_lookup.py`）锁住：
- 名称归一化、双向包含、条款名匹配
- 查不到产品时**不调用检索**
- `product_id` 兜底路径仍可用
